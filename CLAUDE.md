# Rule of Rose decomp — working rules

Matching decompilation of Rule of Rose (PS2, NTSC-U SLUS-214.48) into C++,
as the base for a native PC and then PS Vita port. Current state and
roadmap: `notes/PROJECT_STATE.md` (Spanish). Setup: `README.md` (English).

## Never commit game data

- No ELF, ISO, assets, or disassembly of game code. `disc/`, `asm/`,
  `assets/`, `build/`, `ghidra/` and `matching/**/*.s` are git-ignored;
  keep it that way.
- Committable: our own source, tools, notes, and derived symbol data
  (names, addresses, sizes, types).
- Each collaborator extracts `disc/SLUS_214.48` from their own disc.

## Toolchain

- Matching build: `tools/dock python3 tools/configure.py` then
  `tools/dock ninja`. It must stay green (build/ok = SHA-1 of the load image
  matches). On a mismatch, `tools/.venv/bin/python tools/first_diff.py`.
- File boundaries live in `config/splits.tsv` (from `tools/split_files.py`).
  `unk/<Class>` files are inferred and their names are placeholders; rename
  them when evidence shows the real path, via `config/splits_manual.tsv`
  (hand-made boundaries/names, each with its evidence).
  Moving a boundary is fine and never breaks the asm build; regenerate the
  yaml with `tools/configure.py` afterwards.
- `config/SLUS_214.48.yaml` and `build.ninja` are generated by
  `tools/configure.py`; change the generator, not the output. Hand-written
  symbol fixes go in `config/symbol_addrs_manual.txt`, each with a reason.
- Compiler: **ee-gcc2.96 (SCE), `-Os -G0 -fno-exceptions -fno-strict-aliasing`**,
  confirmed on every function matched so far; `-G0` because no instruction
  uses `$gp`, `-fno-exceptions` because game code has no `.eh_frame`,
  `-fno-strict-aliasing` because the game re-reads values after stores
  through other types. Sources compile from `src/` so `__FILE__` is the
  original relative path.
- Decompiling: follow `docs/DECOMPILING.md` (m2c draft → `tools/match.py`
  until the whole object matches → mangled names in
  `config/symbol_addrs_manual.txt` → full build). Start a file with
  `tools/configure.py --new <file>` (one `INCLUDE_ASM` per function) and
  replace them one by one; partial files keep `.data`/`.bss` in asm.
  Treat other modules' flags as unconfirmed until matched.
- Compile only inside the `ror-build` image (`docker/`), via
  `ee-cc <compiler-id> <gcc args>`. On macOS the docker CLI may live in
  `~/.docker/bin`.
- Python tools run from `tools/.venv` (splat64, spimdisasm, rabbitizer,
  pyelftools).
- Ghidra 12.1.4 + ghidra-emotionengine-reloaded (built from source, see
  README); rebuild the project with `tools/ghidra_setup.sh`.

## Conventions

- Symbols come from `tools/ror_symbols.py`; regenerate rather than editing
  `symbols/*.tsv` by hand. Respect provenance: `linkonce` names are exact,
  `vtable-override` names are inferred (check signatures), `vtable-slot`
  names (`vfunc_NN`) are placeholders, `shared-stub` is `__pure_virtual`,
  `sce-sdb` names come from SDK signatures.
- Never commit PS2Recomp's symbol database (GPL); only derived names.
- Keep original identifiers where the binary reveals them (mangled names,
  assert expressions such as `n>=0 && n<=4`, source paths). Assert calls
  (`FUN_00215a30`) give the original file, line and expression; reproduce
  them with `#line` and the `ASSERT` macro.
- A function counts as done only when it compiles to identical bytes
  (relocations aside). Measure with `tools/compiler_id.py`-style scoring;
  never mark near-matches as matched.
- Ghidra scripts must not overwrite `USER_DEFINED` names or signatures.

## Communication

The project owner writes in Spanish and isn't a reverse-engineering
specialist: explain in Spanish, plainly. Code, commit messages and
developer-facing docs stay in English.
